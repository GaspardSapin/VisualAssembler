### 1.3 Workload (from `arch/m68k/tests/syntax_bench.rs`)

- 100,000 lines made by cycling the 20 fixed lines of the test, joined by LF with no final LF: 3,314,999 B,
  that is 643 content bytes per 20-line cycle (32.15 B per line on average) plus 99,999 LFs.
- Each timed pass runs `va_core::source::lines` over the text and `lex_line` on every line into one
  reused `Vec<Token>` (capacity 64, cleared per line). 1 warm-up pass, then 10 timed passes.
- The token count is asserted after the warm-up and after every timed pass: 222 tokens per cycle,
  1,110,000 in total, which counts every token `lex_line` emits, whitespace included. So no pass
  can skip work without failing the test.
- `median_ms` is the midpoint of the 5th and 6th of the 10 sorted passes; `mb_per_s` uses decimal
  MB (10^6 B) and the median.
- Not measured: the `line_diagnostics` pass (§5.7 completion and quick fixes), file I/O and JSON
  output of `va lex`. An end-to-end `va lex` figure is deferred to M7 (§12.7).

## 4. Analysis

### 4.1 Spread

- **Within a run, 1.5–1.8 % on Windows.** The 10 passes of one process agree closely.
- **Between runs, 4.8 %, and not suspicious.** It comes from one pattern seen twice: the first
  `make bench-lexer` after an idle gap is 4.1–4.8 % slower (W1, after the 12 s gap that followed the
  pre-build: 7.493 ms; W4, after a 20 s pause: 7.399 ms). The runs started right after it agree
  within 0.8 % (7.103–7.157 ms). WSL shows the same shape (L1 the slowest).
- **The whole first process is slower, not just its early passes.** W1's fastest pass (7.412 ms) is
  slower than W2's slowest (7.264 ms), and W1's spread within the run (1.73 %) is normal. The cause was
  not identified. Candidates are the CPU's power state after idle and the core the scheduler picked;
  no per-core frequency or affinity was recorded.
- **No profiling was done** (method step 3). The budget is met 6.7× even by the slowest run, and the
  spread is small and reproducible. The token count, asserted on every pass, rules out skipped work.

### 4.2 Against the developer figure

§12.5 item 5 records the wave-2 developer run: a median of 7.663 ms on "Balanced". Today's 7.157 ms is
6.6 % lower. The code changed since wave 2 (§12.8 fixes, among others) and the power condition differs,
so the causes are not separated. Both figures sit far inside the budget.

### 4.3 Rough indication for the M4 keystroke target

Architecture §7 sets a keystroke-to-frame p95 below 16 ms in a 100,000-line file, with lexer results
cached per line and only the edited line re-lexed. The figures below are arithmetic on the measured
mean and are **not measurements**. The M4 bench is the gate.

| Case | Estimate | Share of 16 ms |
|---|---|---|
| Re-lex one average line (32 B, 11 tokens) per keystroke | 71.6 ns | < 0.001 % |
| Re-lex one line at the 64 KiB limit (65,536 B), scaled linearly at 2.16 ns/B | about 0.14 ms | about 0.9 % |
| Re-lex the whole 100,000-line file on every keystroke (the case the per-line cache avoids) | 7.2 ms | 45 % |
| Lex a 5,000-line project once (the G2 startup case) | about 0.36 ms | — |

- Re-lexing one line costs nothing measurable against the frame budget. The lexer will not be the
  M4 bottleneck; rope edits, layout and painting will.
- Lexing the whole file per keystroke would still fit in 16 ms, but it would take almost half the
  frame. The per-line cache of architecture §7 is therefore needed for the target, and it is
  already planned.
- **Caveat on the 64 KiB line.** It is an extrapolation from the representative mix. Pathological
  64 KiB lines were not timed in release. `robustness.rs` only guards against quadratic behaviour in
  debug (40 lines in under 30 s).

### 4.4 Allocations (not measured)

§12.4 keeps the allocation-free claim a code-review fact in M1, because a counting allocator needs
`unsafe` and an allow-list entry (M7 decides). A read-only grep of `arch/m68k/src/syntax/` matches
allocation calls only in two places:
- `spacing.rs` `complete_diagnostic` and `fix_replacement`: the `line_diagnostics` path, which the
  bench does not run;
- the `OnceLock` keyword list in `keywords.rs`, built once.

Keyword lookup compares with ASCII case folding and allocates nothing (`cmp_folded`). This agrees with
QA's review. The throughput neither proves nor disproves the claim.

## 5. Verdict

**E7: pass.** On the reference machine, on mains with the AC overlay "Best performance", `make bench-lexer`
gives a median of 7.157 ms (463.2 MB/s) over three runs for the §5.6 workload. The budget is ≤ 50 ms
(≥ 65 MB/s), so the margin is 42.8 ms (6.99×). Every one of the 30 timed passes stayed below
7.6 ms, and so did the 60 passes of the replication and WSL runs.

## 6. Changes considered and rejected

| Change | Decision |
|---|---|
| Any optimization of the lexer | **Rejected.** The budget is met 7×, and no profile shows a hot spot. Optimizing on a guess is forbidden. |
| Profiling (method step 3) | **Not done.** It is required only on a budget miss or a suspicious spread. The 4.8 % spread is explained by the first-run-after-idle pattern (§4.1). |
| A criterion bench | **Rejected for M1** by §5.6. M7 decides for all benches. |
| A counting allocator to measure allocations | **Deferred to M7** by §12.4. It needs `unsafe` and an allow-list entry. |
| A release timing of pathological 64 KiB lines | **Not done.** It needs a test change, which is outside this role's write scope. It is a candidate for the M4 large-file bench or M7. |
| Switching the power plan to "Best performance" | **Not needed and not allowed.** The AC overlay was already "Best performance", and changing system settings is forbidden. |

## 7. Reproduce

```bash
make bench-lexer
```

Run it on mains with the power mode on "Best performance", with no other build running. Run it two or
three times back to back: the first run after an idle gap reads about 4 % slow (§4.1).
